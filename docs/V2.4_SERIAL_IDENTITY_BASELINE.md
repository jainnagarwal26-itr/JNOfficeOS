## 3. Mandatory Architectural & Governance Rules

### Rule 1: Technical UUID vs. Business Serial Number
- **UUID (`id`)**: Immutable primary key assigned at record creation. It must **NEVER** change, even during numbering reconciliations or migrations.
- **Business Serial Number (`client_number` / `user_number`)**: Standardized human-readable business serial (`CL000001`, `STF000001`). Once assigned to a production entity, it is **permanently immutable**.

### Rule 2: Backend-Authoritative Sequence Generation
- **Client Serial Numbers**: Generated exclusively by PostgreSQL sequence `public.seq_client_number` via RPC `generate_next_client_number()`. Next available: **`CL000004`**.
- **Staff Serial Numbers**: Generated exclusively by PostgreSQL sequence `public.seq_staff_number` via RPC `generate_next_staff_number()`. Next available: **`STF000003`**.
- **Forbidden Patterns**: Frontend code, `localStorage`, Google Sheets, or local array lengths must **NEVER** generate client numbers or Staff IDs.

### Rule 3: No Number Recycling
- If a client or staff profile is deactivated, deleted, or archived, its issued business serial number (`CL00000X` / `STF00000X`) **MUST NOT be recycled or reassigned** to another entity. The sequence must strictly move forward.

### Rule 4: Centralized Active / Inactive Staff Governance
- **Single Source of Truth**: `public.jn_users.is_active` in Supabase PostgreSQL governs account access globally.
- **Deactivation Enforcement**: Setting `is_active = false` immediately blocks authentication and invalidates sessions across all devices (PC, mobile, incognito).
- **Reactivation**: Setting `is_active = true` restores authentication without recreating profiles or altering roles/permissions.

### Rule 5: Centralized Multi-Device Authentication
- Authentication is strictly user-account-based. Opening the application on a new browser, device, or incognito window must prompt for standard credentials and load existing central profiles from Supabase.
- **Forbidden Pattern**: Device-specific "Create Profile" prompts (e.g. "Create Chirag Jain Profile") or local `passwordHash: ""` fallbacks are strictly prohibited.

### Rule 6: `localStorage` Boundary Restrictions
`localStorage` may ONLY be used for:
- Non-authoritative UI theme/layout preferences
- Temporary offline UI display caching
- Short-lived UI session tokens

`localStorage` **MUST NOT** serve as the source of truth for:
- Client Numbers or Staff IDs
- User Roles or Permissions
- Account Active/Inactive status
- Business data records or compliance filings

## 4. Future Module Integration Guidelines

All upcoming modules (Compliance, Invoicing, Case Management, DMS, GST/ITR Automation, Client Portal) **MUST** reference existing client identities via `client_id` (`jn_clients.id` or `jn_clients.client_number`).

```
Future Feature / Module
          ↓
  Fetch jn_clients.id
          ↓
  Bind to Central Client Identity
```

- **NEVER** create duplicate client records for an existing client.
- **NEVER** introduce alternative client numbering formats or secondary sequence tables.
